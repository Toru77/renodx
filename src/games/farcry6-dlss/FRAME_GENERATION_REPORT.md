# Far Cry 6: DLSS Frame Generation investigation

Date: 2026-10-28. Scope: implementation investigation; no Frame Generation implementation or source changes. Snapshot: one live D3D12 device, 3061 captured operations, TAA draw 2948. The handles and indices below identify this snapshot only and must not be hardcoded.

## SDK

NVIDIA's public releases listed 2.14.16 as latest; no public 2.14.26 release was found. The official x64 2.14.16 package is downloaded at `build/streamline-sdk-v2.14.16.zip` (SHA-256 `32041e51db0cab709a271b72a352281b690c2abbd669a827809401a5dd23956b`, matching NVIDIA's release page). Headers, docs and x64 binaries were extracted to `build/streamline-sdk-v2.14.16`. The production `sl.interposer.dll`, `sl.dlss_g.dll`, `sl.reflex.dll`, and `nvngx_dlssg.dll` have valid NVIDIA signatures. The game's current runtime was not changed. The repository's existing Streamline submodule is 2.8.0; neither it nor global build files were modified.

The user approved keeping SDK headers local to this game. The required headers and license are in `streamline/`. The production `sl.interposer.dll`, `sl.common.dll`, `sl.dlss_g.dll`, `nvngx_dlssg.dll`, `sl.reflex.dll`, and `sl.pcl.dll` were copied next to `FarCry6.exe`; their NVIDIA signatures and hashes against the downloaded SDK were verified. This installation alone does not enable Frame Generation.

The addon now verifies and loads the game-local interposer before D3D12 device creation, without calling `slInit`; Copy Report shows the result. In a separate process, `build/streamline-init-check.exe` successfully called `slInit` with DLSS-G and Reflex requested, created a D3D12 device, called `slSetD3DDevice`, upgraded a DXGI factory, created a swapchain, presented, resized and presented again. Every call returned success, and shutdown succeeded. This is a bootstrap check only: it did not supply FG inputs or generate a frame. A separate late-upgrade experiment also returned success for upgrading an already-created native swapchain and presenting it, but this does not establish a correct FG implementation or override NVIDIA's requirement to intercept swapchain creation.

## Captured frame chain

- Draw 2948: TAA PS `0xFF0AF25B`; 1280x720 RGBA16F RTV `0x250ED1B0B70`; t0 and t1 are 640x360 RG8 packed motion, t2 is 1280x720 RGBA16F scene color, t3/t4 history, t5/t6 1280x720 R8 masks. The selected scene depth is tracked separately by the addon, not identified by these R8 bindings.
- Draw 2949: PS `0x944489F5` reads the TAA RTV as t0 and writes full-resolution 2560x1440 RGBA16F `0x2509ACB2250`, RTV `0x24ED6B519C0`. Blend is off, RGBA writes are on. Its t1 and t2 point to the same 64x64 RGBA8 texture in this snapshot. The decompiled shader contains filtering, edge enhancement and additional sampled modulation. It does not itself demonstrate a full-resolution UI buffer. Our active addon may replace this draw's image with its upscaler output, so the snapshot's original shader metadata alone is not proof of the exact executed pixels.
- Draws 2950 onward: UI-like shader `0x3ED32776` and others (including `0xDC4619B1`, `0x7C01563D`) blend into the SAME full-resolution RGBA16F scene target. For 2950, RGB write mask is `0x7` and blend is source-alpha / one-minus-source-alpha. UI texture at t0 is BC3 sRGB; 2963 additionally samples a 256x256 float texture. Draw 2953 has zero color write mask; it may serve another pipeline purpose, but stencil/depth behavior is not established by this snapshot. These UI shaders were reported as live file replacements; this snapshot is the active mod path, not a clean vanilla baseline.
- Draw 3059: PS `0x62A8D0C3` samples the same RGBA16F scene/UI resource and writes the 2560x1440 `R10G10B10A2_UNORM` swapchain. Decompiled shader decodes a gamma-shaped input, applies color transforms, and uses ST 2084/PQ constants. The current session log reports `hdr10_st2084` and DXGI color space 12, consistent with HDR10/PQ output.
- Draw 3060: alpha-blended indexed draw on the swapchain with PS `0x765C1510`, sampling a 2560x1440 BGRA8 texture. Its disassembly is a plain texture sample. Whether this is DevKit/ReShade overlay or game UI is NOT established. It occurs after the final game output draw in this capture.

A live readback of the 2949/3059 shared float resource found red max 1.2168 and 22,319 pixels with some RGB channel above 1.0; alpha was 1 throughout. This was the resource's current live contents, NOT a readback frozen at draw 2949. It proves neither its pre-UI content nor the frame-generation color-space match. A backbuffer readback using the captured view failed because that view's resource had since been destroyed/recycled. No frame-exact pre-UI or backbuffer image was captured.

## What we have and what is missing

- Depth: existing scene-depth selection and state tracking in `dlss.hpp`; previous Copy Reports show render-sized depth. Need establish correct frame, content and lifetime until the FG present, including menu/resize.
- Motion: existing packed motion decode generates render-resolution RG16F pixel vectors. SL common constants expect normalized motion scale; SDK example for pixel-space vectors is `{1/renderWidth, 1/renderHeight}`. Validate sign, origin, jitter convention, object/foliage coverage, and same-frame identity; current upscaler results alone do not prove FG correctness. Existing unpack output is reused, so establish its lifetime or copy/tag it correctly.
- Jitter: game jitter and injected Halton values are available. Keep the exact value applied for the rendered frame and associate it with that frame's token/present; do not assume the addon present counter equals Streamline's generated/presented frame ID.
- Camera: renderer registration names the camera CB fields: inverse projection at 0x00, inverse view at 0x40, projection at 0x80, view at 0xc0, view-projection at 0x100, current and previous view-rotation projections at 0x140/0x180, viewport at 0x200, current and previous camera position at 0x230/0x240, and right/up/direction at 0x270/0x280/0x290. These names and offsets are static evidence from the version identified in `CAMERA_JITTER_NOTES.md`; the addon now records the values from its identified camera buffer and includes positions and basis in Copy Report. A CPU/GPU copy previously matched 828 bytes for one sampled buffer. The meaning of position fractions, handedness, matrix layout, previous projection and frame pairing still require runtime validation before submitting Streamline constants.
- The game's motion producer `0xD9289B6A` also reads a per-frame 4x4 matrix at b0 c2-c5. The shader first transforms the sampled depth using `(1 - c1.x * depth) / (c1.y * depth)` and uses that result with NDC x/y and the matrix to produce previous x/y. It is a useful reprojection candidate, including depth-dependent terms, but its input coordinate convention must be converted and verified before treating it as Streamline's `clipToPrevClip`. The producer's saved constants are available in the existing Copy Report.
- The camera conversion now builds an unjittered current-to-previous transform from consecutive rotation-projection matrices and camera-position changes. It checks that the previous sample agrees with the engine's own previous rotation-projection matrix; the latest report matched within 6e-8 for all three available frame pairs. Synthetic checks cover jitter removal, translation, rotation, near/far, stale frames and mismatched previous matrices. The user's second report showed a small real position change with a non-identity candidate. The captured last four frames do not establish correctness during large rotations or disocclusions. The candidate is reported but is not yet submitted to Streamline.
- HUD-less: the user has identified the replaced TAA output as the final HUD-less image. Use the active upscaler output at the 2949 handoff as the source, before the game adds UI. Preserve it until present and apply the game's output conversion to match the backbuffer's color space. Do not block implementation on another diagnostic to establish the capture point.
- UI: no completed full-resolution UI alpha or UI-color buffer has been proven. The game blends many draws directly over the scene and RGB-only writes leave existing destination alpha unchanged, so that target's alpha is not a UI mask. Investigate replay/redirect into an independent UI layer or separately accumulate coverage while preserving blend/stencil/order and every shader family. Validate the premultiplied convention and final output color domain; the nonlinear PQ conversion makes a naive linear-domain separation insufficient. An alpha-only mask is the NVIDIA-preferred lower-bandwidth option; an accurately premultiplied UI-color-and-alpha resource enables the SDK's recomposition path. Unsupported UI effects and post-present overlays must be investigated.
- Presentation and Reflex: DLSS-G needs Streamline integration through the game presentation interface, not merely a call at the TAA draw. Initialize Streamline early enough, integrate the swapchain/queue in the documented manual-hooking path, use the game/real-present identity for a per-frame token, and implement required Streamline Reflex markers/pacing. RenoDX `src/utils/dlss/streamline_v2.hpp` contains proxy/interposer and device/queue hook infrastructure, but it is not proof that this game can acquire a Streamline proxy after its swapchain exists. Verify integration order and ReShade coexistence in an isolated prototype. The SDK manual-hooking guide requires presentCommon exactly once per frame; don't signal/tag based on generated present events as though each were a new game frame.
- Startup constraint: ReShade's `create_device` callback runs before D3D12 device creation, but its `create_swapchain` callback exposes only the swapchain description, not a replaceable factory or returned swapchain. The existing RenoDX Streamline hook intercepts a game that already loads the interposer, so attaching it alone does not arrange early Streamline initialization or route Far Cry 6's swapchain through a Streamline proxy. Resolve that handoff before calling `slInit` for a live integration; initializing manual hooking without a proxy presentation path risks the memory growth described by NVIDIA's guide.
- ReShade's factory forwards swapchain creation to its `_orig` factory, while its swapchain calls `_orig->Present` after its own pre-present handling. An appropriately initialized Streamline proxy beneath those wrappers could therefore be a viable integration point, but replacing the factory or swapchain pointer requires preserving ReShade's reference counts, interface versions, queue handling and resize behavior. This path has not been implemented or verified in the game.
- An isolated ReShade factory-hook prototype initialized Streamline, registered the device, upgraded the factory and created a swapchain successfully, but failed on present. A first ReShade-only control was invalid because it called ReShade's D3D12 export directly without its hook trampoline. A corrected ReShade-only fixture using the system D3D12 entry point successfully created, presented and resized its swapchain. With Streamline initialized and an upgraded factory, otherwise similar fixtures failed during present even when the factory wrapper was bypassed; matching the executable and interposer directory did not fix it. The corrected control exposed a ReShade device proxy: one earlier failure passed that proxy to `slSetD3DDevice` rather than the native device. Unwrapping it did not make the Streamline fixture safe. An automatic Streamline proxy experiment also exposed nested Streamline/ReShade device proxies and failed on present. These experiments do not prove the game would behave identically. The unverified hook was removed from the addon.
- Lifetimes: NVIDIA says SL retains references to resources tagged valid until present, but the underlying contents must still not be overwritten or recycled. Use frame-indexed resources and synchronization, not just COM references. In particular, query `slDLSSGGetState` on the present thread and associate `inputsProcessingCompletionFence` and `lastPresentInputsProcessingCompletionFenceValue` with the submitted frame: an addon fence signaled before Streamline's present work cannot establish that DLSS-G has finished reading those inputs. Wait on that fence before reusing or destroying inputs on another queue, as required by SDK section 15.1. Only use volatile tags/copies for resources actually reused; NVIDIA warns that excessive temporary copies cost VRAM. Explicitly clear stale tags, release resources after GPU completion and bound allocations.

## DLSS Super Resolution: Streamline or direct NGX?

Recommendation: keep the proven direct NGX DLSS Super Resolution path for the first FG prototype. Streamline FG does not require replacing that working upscaler merely to tag depth/motion/color and provide common constants. Frame generation still requires correct Streamline initialization, swapchain participation, tags and Reflex. Moving SR as well is a separate migration with potential changes to settings, resource states, ABI, feature lifetime, jitter and frame-token coordination. After FG works, compare a Streamline SR branch against the existing NGX path and migrate only if it materially simplifies behavior or is needed by an identified requirement. FSR should remain independently selectable. Re-evaluate compatibility with the actual SDK/runtime version and installed ReShade before implementation.

## Proposed implementation and verification

1. Use the known HUD-less upscaler output at the TAA handoff, preserving it through presentation and handling the game's final output conversion for SDR and HDR. Validate the result during FG testing, including resolution changes and later overlays.
2. Investigate UI coverage/color by tracing all UI draws and their depth/stencil/blend state, including minimap, text, subtitles, menus and the late backbuffer overlay. Prototype a separate buffer and validate against the actual final image without assuming the target alpha is a mask.
3. Add opt-in, low-overhead camera and resource diagnostics to the existing Copy Report, capturing token/frame IDs, matrix derivation and validation, depth/motion extents/states, target color space, HUD/UI status and lifecycle. Do not enable ongoing costly readback by default.
4. Prototype Streamline initialization, swapchain proxy/manual hooks, Reflex and resource tagging, initially with FG off. Confirm ReShade overlay, resize, fullscreen, alt-tab, game menus, cutscenes and cleanup work. Use the latest SDK files in a game-specific arrangement; agree on a permanent dependency/deployment strategy before modifying shared submodules.
5. Enable FG with explicit support/status checks and a user toggle; validate full-frame camera pan, translation, static background, moving character/foliage, HUD, pause, loading, resolution and HDR/SDR. Confirm generated frames with NVIDIA status and frame pacing, rather than only counter values. Compare resource and VRAM usage before/after repeated switches; report failures and cleanup through Copy Report.

A minimal no-HUD-mask experiment may establish that FG initializes, but it cannot establish final visual quality, correct HUD behavior, or a robust shippable implementation. RTX 40/50 support and HAGS/OS/driver conditions must be queried at runtime; NVIDIA specifies support requirements in the current guide.
